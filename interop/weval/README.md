# Weval Transcript-Scope Conformance Probe

Date: 2026-08-24  
Source investigation: Harmonica HAR-1629  
Weval revision tested: `weval-org/app@26f5a98804d7ba4da17f1a9d92f8ed72784bec6c`  
Blueprint documentation blob: `85d12927c5c46d39f34a30645e060a149794229b`

## Conclusion

Weval's public CLI authoring path does not accept the fully-authored transcript
shape described by its blueprint documentation. The CLI requires every
`messages` sequence to end with a `user` message, so a completed transcript
ending with an authored `assistant` message exits before evaluation.

Removing only that validator guard makes the documented shape run. The
deterministic probe then scores only the final authored assistant message:

| Probe | Expected if whole transcript is scored | Observed |
|---|---:|---:|
| Marker only in the first assistant turn | `1.00` | `0.00` |
| Phrase in the final assistant turn | `1.00` | `1.00` |

This is not a Weval-wide ingestion failure. The same revision exposes a public
evaluation API that accepts canonical blueprint JSON or YAML and invokes the
shared pipeline without the CLI's final-user validator. That API path is
source-confirmed but was not run in this investigation.

The shared evaluator uses the final authored assistant response as its scored
subject and retains the conversation as context. That behavior is appropriate
when a push integration evaluates the latest response. A rubric that evaluates
a multi-turn exchange or whole session still needs explicit subject selection
or aggregation.

## Scope Of Evidence

| Surface | Evidence | Finding |
|---|---|---|
| CLI authoring path | Empirical, unmodified | Rejects assistant-ending `messages` before evaluation |
| Shared evaluation pipeline | Empirical, after removing only the CLI guard | Scores the final authored response; conversation remains context |
| Public Evaluation API | Source-confirmed, not run | Accepts canonical blueprints and bypasses the CLI validator |
| Hosted Weval / WeVal Studio behavior | Not tested | No conclusion |

## Question

Weval's `docs/BLUEPRINT_FORMAT.md` says:

> If the last authored assistant message is a string (non-null), that message
> may be used as the final output if no generation is needed at the end.

It also says judges receive the full transcript. Those statements leave a
critical ambiguity: is the transcript the thing being scored, or merely context
for scoring the final output?

The probe uses deterministic function checks rather than LLM judges, so the
result has no judge variance and requires no interpretation of model output.

## Public API Conformance Target

The tested revision documents `POST /api/v1/evaluations/run`. Its route parses
canonical blueprint JSON or single-document YAML, then calls
`executeComparisonPipeline` directly rather than `validatePrompts` from the CLI.
The API-shaped payload can be submitted in inline mode:

```bash
curl -sS -X POST \
  -H "Authorization: Bearer $PUBLIC_API_KEY" \
  -H "Content-Type: application/json" \
  -H "X-Response-Mode: inline" \
  --data-binary @interop/weval/transcript-scope-api-payload.json \
  "$BASE_URL/api/v1/evaluations/run" \
  | jq '.result.evaluationResults.llmCoverageScores'
```

Inline mode is deliberate: it runs coverage-only and avoids persistence. This
request has not yet been executed against a deployed Weval instance. Until it
is, API ingestion is source-confirmed rather than empirically confirmed.

## Unmodified Run

The command was:

```powershell
$env:STORAGE_PROVIDER = 'local'
$env:UPDATE_LOCAL_SUMMARY = 'false'
pnpm cli run-config local `
  --config evaluation_blueprints/transcript-scope-probe.yml `
  --run-label transcript-scope-probe `
  --eval-method llm-coverage `
  --skip-executive-summary
```

The stock CLI exited with code 1 while loading the blueprint. Calling its
exported validation path directly exposed the exact failure:

```text
Prompt ID 'early-turn-probe': Last message role in the input sequence must be
'user'. Found 'assistant'.
```

The rejection is in `src/cli/commands/run-config.ts:218-222` at the tested
revision:

```ts
const lastRole = messages[messages.length - 1].role;
if (lastRole !== 'user') {
  throw new Error(
    `Prompt ID '${promptConfig.id}': Last message role in the input sequence must be 'user'. Found '${lastRole}'.`,
  );
}
```

This contradicts the same revision's blueprint documentation. The failure is
not an invalid model name, missing key, failed model call, or malformed
deterministic function.

## Diagnostic Patch

The only experimental source change was deleting the final-role guard above.
No generation, evaluator, point-function, parser, or result-aggregation code
was changed.

```diff
- const lastRole = messages[messages.length - 1].role;
- if (lastRole !== 'user') {
-   throw new Error(
-     `Prompt ID '${promptConfig.id}': Last message role in the input sequence must be 'user'. Found '${lastRole}'.`,
-   );
- }
```

The unchanged blueprint then passed validation and completed through the normal
local CLI pipeline.

## Why It Scores The Final Turn

`src/cli/evaluators/llm-coverage-evaluator.ts:1054-1059` constructs the scored
subject this way:

```ts
let subjectText = responseData.finalAssistantResponseText;
const genList = responseData.generatedAssistantTexts as string[] | undefined;
if (Array.isArray(genList) && genList.length > 0) {
  subjectText = genList.join('\n\n');
}
```

For generated conversations, the subject is the concatenation of generated
assistant turns. For a fully-authored transcript there are no generated turns,
so it falls back to the final assistant response.

The full conversation is still available as context. LLM-judged points receive
the transcript separately, with authored assistant messages labelled as fixed.
That does not change the evaluated `<TEXT>`, and deterministic point functions
receive `subjectText`, not the transcript context. The probe therefore
distinguishes context visibility from evaluation-unit selection.

## Ancillary Findings

### Is `models:` required when nothing is generated?

No. A second run omitted `models:`. Weval defaulted it to `CORE` and completed
after the same validator patch:

```text
Models field is missing, not an array, or empty. Defaulting to ["CORE"].
```

The resulting `CORE[temp:0]` identifier was bookkeeping rather than a model
call.

### Does deterministic transcript evaluation call a model?

No. The patched runs completed with no model API keys loaded. The pipeline
registered model and judge providers, but it did not request candidate or judge
output because all turns were authored and all criteria were point functions.

### Does this prove Weval cannot support transcript evaluation?

No. It proves the current CLI authoring path does not support the documented
assistant-ending shape, while the shared pipeline scores the final authored
response. Public source contains a separate API path that bypasses the CLI
validator. Different rubrics may legitimately target one response, several
surrounding turns, or the entire session.

## Implications For OFL And CIP

The probe does not invalidate the push model. It shows that a latest-response
push evaluation and a whole-session evaluation are different contracts. The
public API appears to provide the former ingestion path already; the latter
still needs explicit subject selection or aggregation. CLI parity is a separate
consistency fix, not necessarily a prerequisite for API-based Path B.

The interface should not hard-code either `final_turn` or `transcript` as the
only unit. The appropriate window belongs to the rubric: handling pushback may
need several turns, while a format criterion may need one. A useful contract
therefore needs an explicit target or context-window designation.

This finding complements the draft
[annotation and calibration interface specification](https://github.com/Open-Facilitation-Library/evals/blob/spec/annotation-calibration-interface-v0.1/annotation-interface/README.md)
on the [`spec/annotation-calibration-interface-v0.1`](https://github.com/Open-Facilitation-Library/evals/tree/spec/annotation-calibration-interface-v0.1) branch. That specification
already identifies human annotation exchange, real-session ingestion, and
judge-versus-human validity reporting as layers OFL needs around Weval. This
probe supplies a concrete conformance boundary for evaluation-unit selection
and an API-shaped payload for testing real-session ingestion.
